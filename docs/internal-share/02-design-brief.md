## 1. 誰の、どんな課題か

### プライマリユーザー
**日本の中小・零細の経営者（社長）**  
- 決裁が速い／一人または少人数で情シス・現場を兼ねる  
- 「便利そうだが、何を外に出したか分からない」「社員の勝手な ChatGPT が怖い」  
- 大企業向けの重いガバナンス製品は刺さらない。**今日決めて明日使える**温度感が必要

### セカンダリ
- 実務担当（総務・営業事務など）: 実際に承認ボタンを押す人  
- 将来の情シス兼務者: 監査ログを見て安心したい人  

### 課題（現場のことば）
1. 禁止すると隠れて使う。許可すると説明できない  
2. Bot を増やしても、実行環境が共有だと「誰の手か」が分からない  
3. チャット履歴を残しても、経営が欲しいのは **仕事の事実**（誰が承認し、何をしたか）  
4. ツールのセットアップが面倒で、中小は導入で折れる

## 2. ソリューション化の訴求点（何を約束するか）

### コアプロミス
**「AIを入れるな。AI社員を雇え。」**  
権限・承認・記録がある働き方として AI を採用する。

### 支えるメッセージ（優先順）
| 訴求 | 意図 |
|------|------|
| 社長の承認なしに、AIは（危険なことを）しない | 安心の中心。承認キュー |
| チャット履歴じゃなく、仕事の記録が残る | 監査の価値を経営語に翻訳 |
| 禁止より、採用 | 競合は「禁止ツール」。我々は運用 |
| 面倒な連携はこちらでやる（Managed） | 中小の導入障壁を消す |
| 同じコンピュータでも、職務は分けられる | 共有PCという弱点を正直に言い、制御面で解く |

### やらない約束（信頼のため）
- プロンプト全文を勝手に学習・保管しない（構造化業務事実のみ）  
- 「なんでも自動で買う AI」を売らない（承認と予算が先）  

### Grok Bot 本体との差分（デザインが守る境界）
- Grok Bot = 手足（作業する）  
- 本プロダクト = 名刺・就業規則・日報（権限と説明）  
UI は Grok Bot に寄せつつ、**制御・承認・監査が主役**に見えること。

## 3. 体験の骨格（ユーザー旅程）

1. LP で共感 → 無料トライアル  
2. ダッシュボード到着（すぐ「使える感」）  
3. AI社員を雇う（仕事を言葉で書く → 権限 Draft → 発行）  
4. 危険操作は要対応で社長が承認  
5. 監査で「いま何が起きたか」を一目で見る  
6. 必要なら請求（Stripe: カード／振込）  

デモの見せ場（営業と連携）: **買う前に止める → 承認 → 記録が残る**

## 4. UIUX で意識していること（現行方針）

### 全体トーン
- **Grok Bot 寄せ:** ダーク寄り、落ち着いたニュートラル、紫の汎用 SaaS 感を避ける  
- **中小の社長向け:** 専門用語を減らし、職務・承認・記録の言葉を優先  
- **密度:** エンプラの設定地獄にしない。重要操作は少ないステップ  

### 情報設計（IA）
- サイドバー想定: ダッシュボード / AI社員 / 承認 / 監査 / はじめに / 連携 / 請求 / チーム  
- **AI社員（社員証）がプロダクトの顔。** 連携設定は二の次に見せる  
- 承認キューは「要対応」感（放置すると不安、処理すると安心）  

### コンポーネント方針
- Chip / 状態色: トライアル・承認待ち・拒否・成功を一瞬で判別  
- 空状態は責めないコピー（「まだAI社員がいません。最初の一人を雇う」）  
- ワンタイムシークレット表示は Sealith 的に慎重（一度きり・コピー・警告）  

### LP
- H1 は強く短く。課題は社長の口語  
- 図解: 社員証 → ゲート → 承認 → 監査（4段で足りる）  
- 共有PCの注釈は小さく正直に（隠さない）  

### アクセシビリティ／実装制約
- コントラスト確保（ダークでも本文が読める）  
- モバイルは「承認する」だけでも完結できると強い（将来）

## 5. sealith-web からデザインが借りてよいもの／借りないもの

| 借りてよい | 借りない |
|------------|----------|
| AI設定の「言葉→権限 Draft」フロー | ファイル暗号化・受け渡し体験全体 |
| 要対応／ログのタイムライン感 | 大企業向けの設定の厚みそのまま |
| 職種カード的な Autopilot 感（簡略化） | Sealith ブランドのコピー＆ロゴ |
