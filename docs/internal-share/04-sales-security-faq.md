# 営業向け想定問答 — Grok Bot セキュリティ／共有PC × Staffpass

**対象:** 導入商談で必ず聞かれる論点  
**更新:** 2026-08-23  
**注意:** Grok Bot / Cursor 本体の契約・学習ポリシーは時期で変わる。断定は公式ヘルプ／契約書で最終確認すること。

**関連（法務雛形）:** [利用規約／データ取扱い概要](../legal/README.md)（共有PC・外部連携・承認ゲート条項のたたき台。要弁護士レビュー）

---

## A. 共有PC（実行環境）

### Q1. エージェントごとにパソコンの権限を分けられるのか？
**A（事実）:** Grok Bot の実行用コンピュータは、ユーザー配下で**共有**されることが多い。画面（デスクトップ）はエージェントごとでも、ファイル・入れたツール・ブラウザログインなどは共有されうる。OSだけで「営業Botと経理Botの完全分離」はできない。

**Staffpass が入ると:** 分離の主戦場を OS から **社員証（職務・目的・スコープ・承認）** に移す。同じ箱でも、紐づいた AI社員ごとにできること・残るログ・必要な承認が違う。共有ログインは「環境の能力」、職務権限は Staffpass が fail-closed で握る。

**経営者向け平易語:** Bot分け ≠ 安全。公式も共有コンピュータ。画面が分かれていても境界にはならないので、会社の社員証で分けます。

### Q2. じゃあセキュリティ的に危険では？
**A:** 危険なのは「共有であること」自体より、**境界が無いこと**。Staffpass なしだと、共有環境の能力がそのままエージェントに見える。Staffpass ありだと、Gateway 経由以外は通さない／紐づけ不明は止める／監査に残す、が会社の説明になる。

### Q3. セッションが切れたら紐づけも消えるのでは？
**A（Staffpass設計）:** 消さない。ブラウザセッションと社員証バインディングは別。`employeeId` は固定、トークン再発行は世代だけ上げる。切れたら「要再連携」と明示し、黙ってリセットしない。ヘルスチェックで検知する（生命線仕様）。

## B. データ・海外・学習

### Q4. LLM に投げると海外にデータが行くのでは？特定につながる秘匿情報は？
**A（一般）:** クラウド LLM を使う以上、プロバイダのインフラ・リージョン・契約条件に依存する。日本の中小でも「個人情報・顧客名・未公開情報」は懸念が強い。

**返しの型:**
1. まず **渡してよい情報のポリシー**（社員証の purpose / 禁止事項）
2. 危険操作は **人間承認**
3. 監査で「何を外に出す操作をしたか」を後から説明
4. 秘匿のマスキング（送る前に伏せ字→応答後に戻す）は **別レイヤ／拡張モジュール**（下記 C）

Staffpass 本体の初版は「権限・承認・監査・紐づけ」が中心。マスキング DLP はロードマップ上の隣接プロダクト／オプションとして話すと誠実。

### Q5. Grok Bot はこのチャットを学習に使わない制御ができる？
**A（確認必須）:** 本ドキュメント作成時点で、**Grok Bot 単体の「学習に使わない」公式トグルの有無は、営業が Cursor / xAI の現行契約・ヘルプで確認する**こと。一般に:
- 事業向けプランや契約条項で学習オプトアウトがある製品もある
- コンシューマ設定と企業契約は別
- Staffpass は **学習オプトアウトそのものを保証する製品ではない**（プロンプト全文を制御面に溜めない、という設計はある）

**推奨トーク:** 「学習可否は Bot 側の契約事項。Staffpass は渡す権限と記録を会社が握る。両方セットで説明責任を満たす」

### Q6. Staffpass はプロンプトを全部保存するのか？
**A:** しない方針。保存するのは構造化された業務事実（誰が・何目的で・どのツール・成功／失敗・承認者）。会話全文・CoT は保存しない（P0原則）。

## C. マスキングして投げて戻す制御

### Q7. 秘匿情報をマスキングして LLM に渡し、帰ってきたら戻す、はできる？別プロダクト？
**A:** 技術的には可能（パターン検出・トークン化・往復マッピング）。ただし:

| 観点 | 中身 |
|------|------|
| Staffpass との関係 | **隣接**。社員証の「外に出してよい／だめ」の前段・後段に差し込める |
| 初版に含めるか | 必須生命線（紐づけ・承認・監査）より後が安全。約束しすぎ注意 |
| 別プロダクトか | **モジュール or 別 SKU** が売りやすい（DLP / 秘匿ゲート） |
| 限界 | 100% 検出は無理。人間承認・最小権限とセット |

**営業トーク:** 「興味はある。いま売る本丸は社員証と承認。マスキングは次の拡張として PoC 可能」

## D. Staffpass が入ると「何が変わるか」（一文表）

| よくある不安 | Bot だけ | + Staffpass |
|--------------|----------|-------------|
| 誰の手か分からない | 共有環境 | AI社員ごとに権限とログ |
| 勝手に外部送信・課金 | 止めにくい | 承認ゲート・fail-closed |
| 事故の説明 | チャット履歴頼み | 構造化監査・コストボード |
| セットアップ | 顧客が全部 | Managed で巻き取り可 |
| 紐づけ消失 | 不安 | 永続バインディング＋要再連携 |

---

## E. 商談での順番（推奨）

1. 共有PCの事実を先に認める（隠さない）  
2. Staffpass で境界を移す、と見せる（社員証デモ）  
3. 承認で危険操作が止まる、を見せる  
4. 学習・海外は契約確認＋マスキングは拡張、と正直に  
5. Managed で運用負荷を下げる

## F. 共有PC・ブラウザ・許可ID（柔軟な外部アカウント）

### Q8. Google以外（LINE / X / Instagram など）も社員証に刻める？
**A:** はい。Staffpass の許可モデルは **Google固定ではありません**。

```
AllowedAccount {
  service: string;   // プリセットキー or 自由テキスト（その他）
  accountId: string; // メール / @handle / ページID など
  label?: string;
  browserRequired?: boolean;
}
```

雇うフロー（予算・承認ステップ）の「ブラウザ・外部アカウント」で、JP中小向けチップから選べます:  
**Google / Microsoft 365 / LINE / X / Instagram / Facebook / Slack / その他（サービス名を自由記入）**。  
複数行追加でき、発行時に社員証（Employee / Credential）へ `allowedAccounts` として刻まれ、社員詳細に表示されます。

### Q9. 共有PCのブラウザログインが混ざる問題は、これで完全に消える？
**A（正直）:** **完全隔離はできない**。OS・ブラウザプロファイルが共有なら、既存セッションが別アカウントに見えるリスクは残る。

**Staffpass の緩和策:**
1. **使ってよいIDを社員証に明示**（不一致時は要確認／停止の運用）
2. **browser:use スコープ**をトグルでON/OFF（許可しないならスコープ自体を付けない）
3. **Gateway経由**で監査に残す／権限外は fail-closed
4. **Managed**でツール箱を細くし、無制限ブラウザ直結を載せない
5. ライブの「今ログイン中のID」照合は **部分的**になりうる → ポリシー＋監査＋目視確認で補完（過剰約束しない）

**営業トーク:** 「共有PCの弱点は消えない。だから境界を社員証の許可IDに移し、ズレたら止める／確認する運用にします。GoogleもSNSも同じ枠です。」

### Q10. 実行時に本当にアカウントをチェックするの？
**A:** **欠落／不一致は fail-closed（403）**（ソフト警告のみにはしない・C5）。クレームが許可リストと一致しても承認は always_human。**ライブの「今ログイン中のID」照合は部分的**のまま — 自動ゲート＋Managed目視の二段が現実解。できないことも先に言う。

## G. Auto-review との違い（短）

### Q11. Grok の Auto-review があれば Staffpass は不要？
**A:** 不要にはならない。Auto-review は個人／Bot側の承認ネット。Staffpass は会社の社員証・監査台帳・失効・説明責任。二段。詳細: [`../gateway-vs-auto-review.md`](../gateway-vs-auto-review.md)。
