# Grok Bot に Staffpass の権限を守らせる — 自動 / 手動

**なぜ必要か:** 社員証・予算・承認は、実行体（Grok Bot）がバイパスできたらパスの意味がない。  
**原則:** 危険な能力は Staffpass Gateway の外に出さない。出てしまったら fail-closed と監視で止める／知らせる。

---

## 1. 自動で対応できること（プロダクト実装）

| 制御 | 内容 | 状態 |
|------|------|------|
| **唯一の実行口** | メール送信・発注・外部APIなどは Gateway `/api/gateway/invoke` 経由のみ。直接キーを Bot に持たせない | スタブあり→本番で必須 |
| **社員証検証** | Bearer の世代・失効・purpose/scope チェック | 設計済み・強化中 |
| **永続バインディング** | employeeId ↔ Bot エージェント。切れても黙って消さない／要再連携 | 実装済み |
| **Fail-closed** | 未連携・失効・権限不足は実行しない（403） | 実装済み |
| **承認ゲート** | always_human / risk_based。危険操作はキュー | 実装済み |
| **予算ゲート** | maxPerOrder / day / month。超過は承認 or deny | 実装済み（hire Step3 + spend-gate） |
| **許可外部アカウント** | `allowedAccounts`（service + accountId）。Google固定ではなく SNS/SaaS も刻む。browser:use とセット | hire Step3 + 社員詳細。ライブ照合は部分的 |
| **監査・コスト** | 成功も失敗も社員別に残す | デモ実装済み |
| **ヘルスチェック** | 定期的に「まだ通るか」→ 劣化をダッシュボード表示 | 実装済み |
| **秘密の分離** | 決済・メールの本番シークレットは Gateway／サーバ側のみ | 運用ルール＋実装方針 |

**自動のゴール一文:** Bot が「やりたい」と言っても、Gateway が拒否すれば手は動かない。

---

## 2. 手動・運用で対応すること（特に Managed）

| 制御 | だれが | 内容 |
|------|--------|------|
| **ツール面の削ぎ落とし** | 当社（Managed）/ 顧客IT（BYO） | Grok Bot に無制限ブラウザ・シェル・生の決済コネクタを載せない。Staffpass 経由ツールだけ許可 |
| **環境変数の注入** | 同上 | 社員証トークンと Gateway URL のみ。カード番号や Stripe 秘密鍵は渡さない |
| **初回連携チェックリスト** | 営業〜導入 | 紐づけ確認、テスト承認1件、意図的に権限外を叩いて止まること確認 |
| **アラート対応** | 当社CS / 顧客管理者 | 要再連携・異常コスト・連続 deny を見て声をかける |
| **権限レビュー** | 顧客社長 | 四半期などで少額枠・承認ポリシーを見直す |
| **インシデント** | 双方 | 失効ボタンで即停止、世代ローテ、事後監査 |

---

## 3. バイパスが起きうる場所（正直に）

1. Bot に **Gateway 外の強力ツール** が残っている  
2. ユーザがチャットで **別サービスにログイン情報を貼る**  
3. 共有PC上の **既存ブラウザセッション** を悪用する操作（別Google / SNSにログインしたまま等）  
4. Staffpass を通さない **手作業の並行ルート**（人間が別途決済）

→ 1は設定で潰す（最重要）。2–3は **許可IDを社員証に刻む**＋ポリシー・教育・承認・Managed目視。ライブID照合は完全ではない。4は業務設計。

---

## 4. 推奨アーキテクチャ（守り方）

```
[Grok Bot エージェント]
  許可ツール: staffpass.* のみ（一覧・下書き申請・発注申請など）
       ↓ HTTPS + 社員証
[Staffpass Gateway]
  検証 → 予算 → 承認 → 実API（Stripe/メール等）
       ↓
[監査 / コスト / バインディング]
```

Bot に「Stripeを直接叩く」「任意URLにPOST」を与えない。

---

## 5. 雇うフローとの接続

補足ヒアリングで決めた承認・少額枠・**ブラウザ許可／外部アカウントID**は、**社員証に刻み、Gateway が評価**する。  
画面の設定と実行時制御が一致していることが「パスの意味」。

**ブラウザ・許可IDの限界メモ:** ランタイムで「今のブラウザが許可IDと一致するか」は環境によって部分的。未設定で `browser:use` すると Gateway スタブは **warning** を返す。止めきれない共有セッションは監査と Managed チェックで補う。

---

## 6. 営業・導入での言い方

> Staffpass のルールは、お願いベースではなくゲートで強制します。  
> 自動で止められることは止め、Bot側の道具箱は当社（または情シス）が手で細くします。  
> 共有PCの弱点は残るので、境界を社員証に移したうえで監視します。

---

## 7. チェックリスト（導入時）

**自動確認**
- [ ] 紐づけ status = linked  
- [ ] 権限外 invoke が 403  
- [ ] 承認必須の操作がキューに入る  
- [ ] 少額枠超過が止まる（設定時）  
- [ ] ブラウザ利用時に許可外部アカウントが社員証に入っている（未設定なら警告）  

**手動確認**
- [ ] Bot のツール一覧に危険な直結が無い  
- [ ] シークレットが Bot 会話に出ていない  
- [ ] 管理者に要再連携の見方が伝わっている  
- [ ] 許可IDと実ブラウザ／SNSログインが一致している（共有PC）

## 8. Managed 生命線デモ文言（P0 揃え）

営業・導入デモで必ず見せる／言うこと:

> 「この AI社員の ID は一度発行したら変わりません。トークンは最初の手渡しだけ。連携が切れたら画面に **要再連携** と出して、黙って消しません。」
>
> 「送信・日程確定・発注は Gateway で必ず人間承認に上げます。空き枠の提案や下書きだけ自動にできます。」
>
> 「Bot の道具箱には Staffpass 経由だけを残します。直結のメール送信や決済キーは渡しません。」

実装対応: `docs/binding-lifeline.md` / `POST /api/gateway/invoke`（purpose・jobId・allowlist・confirm/send → needs_approval）。
